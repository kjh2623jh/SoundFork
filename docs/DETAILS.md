# SoundFork 상세 설명

**한국어** | [English](DETAILS.en.md) · [사용자 안내](../README.md) · [개발 안내](DEVELOPMENT.md)

SoundFork가 오디오를 전달하는 방식, 지원 조건, 지연과 검증 범위를 설명한다.
설치와 기본 사용은 README를, 소스 수정·빌드·테스트 명령은 개발 안내를 참고한다.

## 지원 범위와 호환성

SoundFork는 DJMAX나 FiiO 전용 후킹 프로그램이 아니다. 표준 64비트 ASIO COM
인터페이스로 실제 드라이버를 열고, 게임이나 DAW에 SoundFork라는 ASIO 드라이버를
노출한다. 채널·샘플레이트·버퍼 크기 등 재생 조건은 실제 드라이버에 질의한다.
다른 제조사 드라이버에서도 사용할 수 있는 구조지만 모든 드라이버의 호환성을
검증한 것은 아니다. 현재 실사용 확인 환경은 DJMAX RESPECT V와 FiiO K11 R2R이다.

방송용 복제에는 별도의 제한이 있다.

- Windows 10/11 x64와 64비트 ASIO 호스트를 대상으로 한다.
- 48 kHz, 출력 채널 0·1의 스테레오, `ASIOSTInt32LSB` 형식을 지원한다.
- 복제 블록 크기는 1~8,192프레임이며, 실제 버퍼 크기는 하드웨어 드라이버가 지원해야 한다.
- 프로세스당 준비된 ASIO 스트림 하나만 허용한다.
- 다른 샘플 형식·샘플레이트·채널 배치는 ASIO 재생이 가능하더라도 방송용 복제가 활성화되지 않을 수 있다.
- OBS 전용 플러그인은 OBS Studio 32.2.2 이상 x64를 대상으로 한다.

64 samples는 FiiO 검증 환경의 설정이지 모든 드라이버에 강제하는 값은 아니다.
제조사 ASIO 드라이버는 먼저 설치해야 하며 SoundFork가 대신 제공하거나 수정하지 않는다.

## 오디오 경로와 실행 구성 요소

```text
게임 / DAW → SoundFork ASIO 프록시 → 하드웨어 ASIO 드라이버 → DAC
                       └→ 오디오 복제 → 캡처 허브
                                          ├→ OBS 전용 소스
                                          └→ 릴레이 → 가상 재생 장치
                                                        ├→ Discord 전체 화면 공유
                                                        └→ OBS 장치 캡처
```

게임은 실제 드라이버가 소유한 출력 버퍼에 직접 쓴다. SoundFork가 게임 재생을 위해
별도 큐나 재생 스레드, 한 버퍼 주기 대기를 추가하지 않는다. 방송용 데이터는 별도로
복사하며, 방송 소비자가 늦으면 복제 블록만 버리고 DAC 출력은 기다리지 않는다.

- `soundfork_driver.dll`: 게임 프로세스 안에서 로드되는 ASIO 프록시다. 별도 EXE가 아니다.
- `soundfork_control.exe`: 하드웨어 드라이버 선택, 상태 확인, 릴레이·플러그인 관리를 담당한다.
- `soundfork_capture_hub.exe`: 복제된 오디오를 OBS와 릴레이에 각각 분배한다.
- `soundfork_discord_relay.exe`: 방송용 오디오를 가상 재생 장치로 출력한다.
- `soundfork-obs.dll`: OBS 프로세스 안에서 로드되는 오디오 소스 플러그인이다.

허브는 OBS 소스나 릴레이가 필요할 때 자동으로 실행되며, 양쪽 소비자가 모두 종료되면
약 2초 뒤 종료된다. 게임이나 허브가 재시작하면 소비자가 다시 연결한다. 진단용
`soundfork_capture_monitor.exe`는 원본 오디오의 단일 소비자이므로 허브와 함께 실행하지 않는다.

제어판은 재생의 필수 구성 요소가 아니다. 릴레이 실행 중에 창을 닫으면 트레이에
남으며, 제어판만 종료해도 실행 중인 릴레이와 ASIO 재생은 계속될 수 있다.
언어는 최초 설치 선택으로 초기화하고 이후 사용자 선택을 저장한다. 저장된 설정이
없으면 Windows UI가 한국어일 때 한국어, 그 밖에는 영어를 사용한다.

## 지연과 방송 안정성

### 게임 재생 지연

SoundFork가 추가하는 **버퍼 지연의 이론적 하한은 0 ms**다. 이것은 실제 입출력
지연이나 프록시의 CPU 처리 시간이 0이라는 뜻이 아니다. ASIO 드라이버, USB, DAC와
게임 자체의 지연은 존재하며 복제 작업에도 실행 시간이 든다.

48 kHz / 64 samples의 한 버퍼 주기는 계산상 약 1.33 ms다. SoundFork가 그 주기를
추가로 기다리는 구조는 아니며, 이 계산을 실제 지연 측정값으로 취급하면 안 된다.
검증 환경에서 직접 ASIO와 프록시는 모두 출력 지연을 168 samples로 보고했다.
이것도 **드라이버 보고값**이며 물리 루프백으로 측정한 지연이 아니다.

2026-10-19의 가짜 ASIO 백엔드 Release 가속 시험에서는 10,800,000콜백 중 매
4,096번째 콜백을 표본으로 측정해 평균 0.121 us, 최대 7.7 us를 기록했다.
이 수치는 해당 PC의 synthetic 콜백 실행 시간이지 실제 FiiO 지연 측정값이 아니다.

### 방송용 지연과 장애 격리

하드웨어 ASIO와 가상 WASAPI 장치는 서로 다른 클럭을 사용한다. 릴레이는 방송
경로에서만 목표 큐 4블록과 ±2,000 ppm 범위의 적응형 리샘플링으로 드리프트를 보정한다.
48 kHz / 64 samples에서 4블록은 계산상 약 5.33 ms이며, 여기에 WASAPI·캡처 앱의
버퍼링 등이 더해질 수 있다. 게임 재생 경로에는 이 큐나 리샘플링을 적용하지 않는다.

OBS 플러그인은 480프레임 / 10 ms 단위로 오디오를 전달하고 잔여 큐와 클럭 보정을
사용한다. OBS 내부 버퍼와 영상 동기화도 있으므로 가상 장치를 생략했다고 최종 녹화
지연이 반드시 줄어든다고 단정할 수 없다. 비교 녹화와 실제 측정이 필요하다.

OBS 큐가 밀려도 릴레이와 DAC를 기다리게 하지 않는다. 가상 WASAPI 장치가 제거되거나
오디오 서비스가 재시작되면 릴레이는 연결을 다시 열도록 구현되어 있다. 이 복구는
ASIO 재생을 중지하지 않지만, 실제 하드웨어 드라이버나 DAC 자체의 연결 해제를
SoundFork가 무중단 재생으로 해결한다는 의미는 아니다.

## Discord와 OBS의 차이

ASIO는 Windows 공유 오디오 엔진을 우회한다. FiiO로 직접 보낸 ASIO 소리는 일반
WASAPI 루프백에 나타나지 않으며, 릴레이가 만드는 Windows 오디오 스트림의 소유자는
게임이 아니라 `soundfork_discord_relay.exe`다.

기존 원격 청취 시험에서는 다음을 확인했다.

- DJMAX 애플리케이션 창 공유: 릴레이를 사용해도 게임 소리가 포함되지 않았다.
- 전체 화면 공유 + 직접 ASIO: 게임 소리가 포함되지 않았다.
- 전체 화면 공유 + SoundFork 릴레이 + VB-CABLE: 게임 소리가 포함되었다.

따라서 SoundFork의 Discord 지원 방식은 **전체 화면 공유**다. Windows 11의 공개
스트림·창 연결 API도 시험했지만 Discord 창 공유에 외부 릴레이 소리가 포함되지 않았다.
게임 코드 주입이나 Discord 비공개 API를 사용하지 않으며, 게임 소리를 마이크 입력으로
보내는 것을 화면 공유 지원의 대체 수단으로 취급하지 않는다.

OBS 전용 플러그인은 허브에서 오디오를 직접 받으므로 가상 장치나 릴레이가 필요 없다.
Discord도 함께 사용한다면 릴레이를 켜고 OBS에서는 전용 소스로 받을 수 있다.
가상 장치 방식에서는 SoundFork와 OBS 모두 같은 재생 장치를 선택한다. VB-CABLE은
`CABLE Input`이 재생 장치이며 `CABLE Output`은 녹음 장치다.
OBS에서 같은 소리를 전용 소스와 장치 캡처로 동시에 받으면 중복된다.

OBS 안에서는 SoundFork 소스를 하나만 만들고 다른 장면에서는 기존 소스를 재사용한다.
서로 다른 OBS 프로세스 여러 개의 동시 직접 캡처는 지원하지 않는다. 플러그인과
릴레이는 같은 SoundFork 빌드의 구성 요소를 사용한다.

## 설치와 플러그인 관리의 동작

설치 프로그램은 등록된 x64 ASIO 드라이버를 선택받아 SoundFork를 등록한다.
기존 백엔드가 유효하면 유지하고, 없으면 FiiO ASIO Driver를 우선 선택한다.
호환 드라이버가 하나도 없으면 제조사 드라이버 설치를 안내하고 중단한다.
하드웨어 드라이버나 가상 장치를 삭제하지 않으며 Windows 기본 오디오 장치도 바꾸지 않는다.

OBS 플러그인은 선택 설치하며, 나중에 제어판에서 설치·업데이트·제거할 수 있다.
설치 상태와 버전 조회에는 관리자 권한이 필요하지 않다. 파일 작업을 선택할 때만
관리자 승인을 요청하고 OBS가 실행 중이면 파일 교체·제거를 거부한다.
볼륨과 음소거는 OBS에서 조절하며 제어판에 별도 오디오 전달 스위치는 없다.

일반 OBS 설치 경로는 `%ProgramData%\obs-studio\plugins\soundfork-obs`다.
SoundFork 설치 폴더에는 플러그인 설치를 선택하지 않아도 원본을 보관한다.
Portable OBS는 이 ProgramData 경로를 검색하지 않으므로 DLL과 허브 EXE를
`obs-plugins\64bit`에, 플러그인의 `data` 내용을 `data\obs-plugins\soundfork-obs`에
수동 배치해야 한다. 제어판 관리는 일반 설치 경로를 대상으로 한다.

## 검증 기록과 남은 확인

날짜별 시험 기록이며, 모든 드라이버·PC·향후 릴리스에서 같은 결과를 보장하지 않는다.
실행 명령과 재현 절차는 [개발 안내](DEVELOPMENT.md#테스트와-진단)를 참고한다.

- 하드웨어 환경: FiiO ASIO Driver 6.16.0.0, FiiO K11 R2R, 48 kHz / 64 samples,
  스테레오 `ASIOSTInt32LSB`. 사용자는 좌우 재생, 체감 지연 차이 없음, 클릭·팝·드롭아웃
  없음과 게임 재실행을 확인했다. 곡 전체·장시간 연속 재생 검증과는 구분한다.
- 2026-10-19: 등록된 COM 경로의 3초 소비 구간에서 2,244블록 / 143,616프레임과
  생산자 드롭 0을 기록했다. Release Setup 설치·제거와 OBS의 `CABLE Input` 데스크탑
  오디오 캡처도 실사용 환경에서 확인했다.
- 2026-10-19 가속 시험: 4시간 등가 10,800,000콜백과 ±1,500 ppm 릴레이 드리프트를
  시뮬레이션했다. 생산자 드롭 0, 소비자 언더런 0, 최대 큐 1블록, 시작·종료 private
  bytes 동일을 기록했다. **실제 시간으로 4시간 하드웨어를 재생한 시험이 아니다.**
- 2026-10-20 로컬 회귀: OBS 플러그인 포함 Debug·Release CTest 각각 10/10,
  보안 도구 테스트 30개 통과와 실제 ClamAV 테스트 1개 건너뛰기를 확인했다.
  기존 MSVC AddressSanitizer 프록시·공유 링·릴레이 시험 및 `/analyze /WX` 통과 기록도 있다.
- 2026-10-21 OBS 수정: 사용자는 rc.2 전용 소스에서 게임 소리의 끊김·잡음을 보고했고,
  같은 환경의 VB-CABLE 출력 캡처와 마이크·브라우저 소리는 정상이라고 확인했다.
  기존 코드의 8초 libobs 파형 검사에서 불연속 10회와 무음 구간 5회를 재현했다.
  타이머 지연 시 누락된 전송을 따라잡도록 고친 뒤 파형 검사를 통과했다. OBS에만
  최소 20 ms 잔여 버퍼, 언더런 후 재충전, MMCSS와 원인별 통계를 추가했다.
  가상 4시간 지터·±1,500 ppm 시험도 통과했다. ASIO 재생·WASAPI Relay 코드는
  변경하지 않았으며, 수정된 플러그인의 실제 DJMAX 녹화와 물리 지연 측정은 아직 남아 있다.
  Debug·Release CTest 각각 12/12, OBS 타이밍·파형·복구 검사 각각 3회 반복,
  `/analyze /WX`, CFG·NX·ASLR·정적 런타임 검사도 통과했다. 정상 파형 검사에서
  불연속·무음 구간·언더런·블록 폐기·재동기화·OBS 출력 드롭은 0이었다.
  의도적인 생산자 중단 시험에서는 언더런 후 회복을 확인했다. 별도 ASIO 가속
  4시간 시험도 생산자 드롭·소비자 언더플로 0이었으며 실제 하드웨어 soak는 아니다.
- 허브·실제 libobs 자동 테스트는 좌우 PCM, 타임스탬프 증가, 느린 소비자 격리,
  게임·허브 재시작과 릴레이 동시 수신을 검증한다. 실제 OBS UI 녹화 결과를 대신하지 않는다.

아래 항목은 완료했다고 주장하지 않는다.

- 모니터에서 DJMAX 곡의 0이 아닌 PCM을 확인하는 시험과 실제 시간 4시간 동시 soak
- 가상 WASAPI 장치의 실제 드라이버 제거·재연결 시험
- 실제 마이크와 Discord 전체 화면 공유의 동시 원격 청취 확인
- FiiO·Discord·OBS 전용 플러그인 동시 녹화의 영상·음성 싱크와 장시간 안정성
- 물리 루프백을 이용한 입출력 지연·프록시 추가 지연 측정
- 새 플러그인 관리 기능의 실제 UAC 승인·취소와 설치·제거 전체 과정, 실제 링크·정션 거부 시험

## 보안 검사와 신뢰 범위

공유 메모리는 크기·오프셋·포맷을 검증하고, 콜백은 검증한 크기를 내부에 캐시한다.
버퍼 페이지는 시작 전에 접근한다. 이는 손상된 헤더에 대한 방어이지 같은 사용자
권한의 악성 프로세스를 차단하는 보안 경계가 아니다.

CodeQL은 C/C++ 소스를 분석하고 Dependabot은 Actions 의존성 업데이트를 확인한다.
보안 검사 워크플로를 포함한 릴리스는 최종 설치 파일·ZIP·추출 내용을 ClamAV로 검사하며
탐지나 검사 실패 시 게시를 막는다. 기존에 게시한 릴리스를 자동 재검사하거나 교체하지 않는다.
검사 방법과 운영 절차는 [개발 안내](DEVELOPMENT.md#보안-검사-운영)에 있다.

README 배지는 워크플로 실행 상태이지 특정 파일의 안전 인증이나 취약점 0개 표시가 아니다.
단일 백신 엔진은 악성코드 부재를 보장하지 않으며, 보안 검사는 코드 서명·SmartScreen
평판·하드웨어 시험을 대체하지 않는다. 실제 검사 여부는 해당 릴리스의 Actions 기록으로 확인한다.
